# Piko engineering audit — 2026-11-16

## Method and evidence

Inspected the real `oakvx/piko` default branch, 75 repository entries including all Python runtime modules, Tauri launch code, Workfield TypeScript client/UI, installer scripts, tests, and GitHub Actions. Compared source behavior to the acceptance directive. Original default branch `1eb0866`; original main workflow [43919464892](https://github.com/oakvx/piko/actions/runs/43919464892) failed in Windows Tauri Rust E0597. The isolated Rust correction was compiled in [43924669516](https://github.com/oakvx/piko/actions/runs/43924669516), which passed Python, frontend and Windows NSIS jobs; no prerelease is published from PR branches.

Labels are **IMPLEMENTED**, **TESTED** (synthetic fixtures only unless specified), **PARTIAL**, **MISSING**, **BROKEN**, and **BLOCKED**. Passing unit tests must never be interpreted as real Windows desktop or real Ollama validation.

## Concrete defects addressed in the audit branch

1. Tauri Rust E0597 drop-lifetime failure prevented NSIS packaging; corrected and verified by a green Windows packaging job on isolated commit `54c493b`.
2. SQLite omitted active plans from disk but retained nonterminal session status. Nonterminal sessions now fail closed on restart and historical states are exposed read-only.
3. `asyncio.wait_for(to_thread(...))` could give up input ownership while Windows native work continued after timeout. Dispatch task is now shielded and joined before input ownership is released. A hung native call remains an unresolved limitation.
4. Teach metadata serialized raw Edit/Text values, dynamic text-derived UIA identifiers and window titles. These are now redacted from the JSON timeline. Explicitly authorized screenshots may still contain visible personal information.
5. Existing API test waited a fixed 50 ms for background execution and failed intermittently on Windows runners. Changed to bounded terminal-state polling.
6. Duplicate CI jobs from push and pull_request events; limited push trigger to `main`, retained PR checks.
7. Corrected artifact naming and stale documentation; introduced lint and security regression coverage.

## Remaining release blockers and risks

- **Critical verification gap:** No clean Windows 10/11 x64 install/upgrade/uninstall/relaunch validation or offline controlled GUI automation run.
- **High:** `WindowsDesktop.emergency_release` is a no-op and UIA calls cannot guarantee immediate cancellation.
- **High:** Foreground-app identity can change between an authorized observation and a native action (TOCTOU). Stronger process/window-bound execution is required.
- **High:** A task can use an `exists` expectation for a pre-existing element, proving only presence, not causal completion.
- **High:** Screen recording produces unredacted screenshots of explicitly authorized windows; build user-visible review and sensitive-content policies before general use.
- **Medium:** No pinned npm lockfile or Cargo.lock committed. Python dependency ranges are also not fully resolved to a lock.
- **Medium:** No fully featured Teach event synchronization, reusable verified Skill runner, robust SQLite schema migrations, or 13-surface UI coverage.
- **Blocked externally:** Real Ollama inference, GPU/CPU benchmarks and hands-on Windows accessibility/desktop tests require a compatible controlled physical or virtual Windows test environment with installed models.

## Required gate before stable release

Verify clean-machine NSIS installation, authenticated sidecar and shutdown, local reasoning/vision inference, permission-scoped UIA task with observable outcome, Teach event-to-Skill generation and replay, reboot persistence, cancellation under held input, high-DPI/multimonitor, negative authorization tests, installer extraction/checksum, uninstall and upgrade. Do not represent a passing CI build alone as production readiness.

## Development sequence

1. Merge only a fully green, reviewed audit PR and confirm `main` prerelease assets and checksum.
2. Bind input actions to expected process/window identity and implement concrete input-release tracking and native-call timeout containment.
3. Expand Teach to synchronized local permitted input timeline, correction loop, parameterized Skill creation and safe verified replay.
4. Add migration/versioning, Skill rollback and retention/purge controls.
5. Expand original Workfield without imitating another AI dashboard, then execute the full 27-step Windows acceptance sequence with evidence.
